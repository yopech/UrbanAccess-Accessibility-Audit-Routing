# Фаза 0: безопасное сохранение в React и PWA

## Объём

Реализованы шаги 0.5 и 0.6. Добавлены React-каркас Vite, контроллер редактора, хук внешнего хранилища, базовые индикатор сохранения и диалог конфликта, совместимость с прежним маршрутным интерфейсом и единый управляемый Service Worker. Экран обследования входной группы и доменные команды фаз М1 не реализуются в этом шаге.

## Контроллер редактора

`frontend/src/features/editor/editor-controller.ts` хранит отдельно подтверждённый агрегат, команды текущего коммита и новую очередь правок. `enqueue(command)` сразу обновляет оптимистичный снимок. До изменения очереди проверяется возможность применения команды. Debounce составляет 1000 мс после последнего ввода.

`getSnapshot()` возвращает стабильный объект до изменения состояния. `subscribe` возвращает функцию отписки. `useEditorController` подключает эти методы через `useSyncExternalStore`, без глобального React-контекста фотографий.

`flush()` отменяет debounce и возвращает Promise, который завершается после записи в IndexedDB. Параллельные вызовы получают одну операцию сохранения; второй commit одновременно не запускается. Команды, поступившие во время записи, остаются отдельной очередью и применяются к подтверждённой новой ревизии. Завершение предыдущего пакета не заменяет новые ручные правки.

Результат `flush`: `saved` с подтверждённой ревизией либо `blocked` со статусом ошибки/конфликта. Ошибка сохраняет очередь. `retry()` выполняет явный повтор ошибки; при конфликте автоматического повтора с новой ожидаемой ревизией нет.

Хук инициирует flush при потере фокуса, скрытии документа, `pagehide` и размонтировании. `flushBeforeTransition(controller, transition)` ожидает успешное сохранение перед переключением зоны, элемента, экрана или запуском экспорта. Компоненты следующей фазы должны использовать этот метод для переходов. При размонтировании блокировщик обновления сохраняется до успешной записи оставшейся очереди. React Strict Mode не дублирует постоянные подписки.

`beforeunload` предупреждает о непринятых изменениях. Принудительное завершение процесса браузера не гарантирует завершение асинхронной записи; событие закрытия не считается надёжным механизмом сохранения.

## Конфликт ревизий: AC-15

Ответ `conflict` оставляет прежнюю базовую ревизию и все локальные команды. Редактор показывает собственные правки и актуальную версию отдельно. Очередь остановлена до явного решения пользователя.

`RevisionConflictDialog` использует доступный Radix Dialog: сравнение двух версий, загрузка актуального агрегата и, при подключённом обработчике, сохранение независимой копии. `loadLatest()` явно отбрасывает локальную очередь и загружает текущий агрегат. `saveIndependentCopy(makeCommands)` создаёт новый UUID и коммит с `expectedRevision: 0`; исходное обследование не перезаписывается. Функцию команд создания копии предоставляет доменная модель редактора.

`SaveStatusBadge` показывает saved, dirty, saving, error, conflict. Ошибка остаётся видимой; исчезающий toast не используется вместо статуса.

## Совместимость маршрутов

`LegacyRoutesHost` вызывает `mountLegacyRoutes(root)` и освобождает mount при уходе. Прежний код использует глобальные селекторы, поэтому выбран отдельный same-origin документ `legacy.html` внутри iframe. Его DOM и стили изолированы от React, бизнес-правила не переписываются. Удаление browsing context освобождает его обработчики и таймеры; дополнительные обработчики моста снимаются явно.

Старый `db.js` использует новый общий `openDatabase()` версии 3. В legacy больше нет регистрации собственного SW. Начальные записи, индексы и Blob сохраняются добавочной миграцией. Экспорт старых данных проверяется через реальный интерфейс.

Мост отмечает изменённые формы, незавершённые асинхронные операции и активную диктовку. На время подготовки обновления документ становится `inert`. При отказе обновления доступ возвращается. Legacy-форма сама не сохраняется автоматически: пользователь завершает или явно сбрасывает её. Это сохраняет существующие требования полевого сбора.

## PWA и AC-20

`vite-plugin-pwa` настроен на `injectManifest` и prompt. Регистрация выполняется только `PwaUpdateController`. SW публикуется по прежнему пути `frontend/sw.js`. Установка precache не вызывает безусловный skipWaiting. В кеш входят HTML-каркас, legacy-формы, все JS/CSS-ресурсы и локальные Inter WOFF/WOFF2. Лимит одного файла увеличен до 10 МБ. Формы следующей фазы и экспортные chunks попадут в тот же glob при появлении в сборке.

Порядок обновления:

1. Новая версия устанавливается в waiting; приложение показывает кнопку и продолжает работу.
2. Пользователь нажимает кнопку обновления. Waiting worker опрашивает все верхние окна своего scope, включая ещё не контролируемые. Вложенный legacy-документ представлен участником родительской вкладки.
3. Каждая вкладка замораживает начало новых правок, ожидает `flush()` всех зарегистрированных редакторов и проверяет блокировщики. Экспорт и голосовой контроллер следующей фазы подключаются через `updateParticipants.add` с тем же интерфейсом `prepareUpdate/releaseUpdate`.
4. Worker ожидает ответы до 5 секунд и повторно сверяет состав окон. Ошибка, конфликт, несохранённая legacy-форма, активная операция или отсутствие ответа откладывают обновление. Участники размораживаются; версия и данные остаются прежними.
5. Только при готовности всех окон worker сообщает UPDATE_ACCEPTED и вызывает skipWaiting. Перезагрузка допускается после согласованной подготовки; обычный controllerchange при первом запуске не перезапускает страницу.

Очистка кешей ограничена собственным префиксом UrbanAccess. IndexedDB не очищается при обновлении. Hash-навигация и единый Vite base сохраняют путь установки. Первый переход с прежней статической поставки может потребовать закрытия старых вкладок: они ещё не поддерживают новый протокол подготовки.

## Проверки и сборка

- `pnpm typecheck`: строгий TypeScript приложения и отдельная проверка SW.
- `pnpm test`: прежние доменные проверки.
- `pnpm test:editor`: очереди, debounce, ожидание коммита, ошибки, конфликт, Strict Mode-подписки и подготовка обновления.
- `pnpm test:storage`: нативная IndexedDB, миграция, конкурентные коммиты и откаты.
- `pnpm test:phase0`: две реальные production-сборки и браузерные сценарии AC-15, AC-19, AC-20, холодный запуск/экспорт без сети, повторное монтирование legacy.
- `pnpm build`: production без тестового редактора, `dist/frontend` и корневой переход в `dist/index.html`.

Браузерный тест временно включает отдельную QA-точку входа через `URBANACCESS_TEST_BUILD=1`. Обычная сборка не содержит её. Публикация выполняется из `dist`; исходный React/TypeScript не публикуется как готовая статическая страница. В этом шаге публикация на GitHub не выполняется.
