# Фундамент хранения обследований: фаза 0, шаги 0.3 и 0.4

Реализованы общие TypeScript-контракты и независимый слой хранения обследований на нативной IndexedDB. UI, стили, Service Worker и доменные команды редактора относятся к следующим шагам.

## Файлы и интерфейсы

- `frontend/src/domain/contracts.ts`: идентификаторы, даты, ревизии, Actor, Confirmation, VersionRef, CommitEnvelope, CommitResult, SaveState, StorageError и нормализация ошибок браузера. Общие контракты соответствуют разделу 0.4 плана.
- `frontend/src/storage/database.ts`: `AuditDatabase.open()` и `close()`, добавочная миграция, проверка схемы и обработка жизненного цикла соединения.
- `frontend/src/storage/audit-store.ts`: `AuditStore<T, C>` с `load(id)`, `list()`, `commit(request)`, `subscribe(listener)` и `close()`.

`T` расширяет `StoredAudit`: `id`, `objectId`, `schemaVersion`, `revision`, `status`, `updatedAt`. Это минимальный контракт хранения, который будущая полная модель Audit дополняет зонами, элементами и другими данными. `C` представляет доменную команду. В конструктор передаётся синхронная чистая функция `reduce(current, commands, context)`, применяющая пакет команд к актуальному агрегату. Можно передать синхронный валидатор полной модели. Асинхронные обработчики отклоняются с ошибкой и не создают записей.

`load` возвращает запись либо `undefined`; `list` возвращает массив в порядке первичных ключей, а не времени изменения. Ошибки чтения отклоняют Promise с `StorageError`. `commit` возвращает один из вариантов `CommitResult`: `committed`, `conflict`, `failed`.

## Схема базы

Имя production-базы: `urban-accessibility-field-v1`. Версия: **3**. Отдельная опция имени базы предназначена для изолированных тестов. Версия записи `schemaVersion` не равна версии базы.

| Хранилище | Ключ | Имена индексов и их keyPath |
|---|---|---|
| `audits` | `id` | `updatedAt`, `status`, `objectId` |
| `auditPhotos` | `id` | `auditId`, `elementId` |
| `auditEvents` | `id` | `auditId_revision`: `[auditId, revision]`; `transactionId` |
| `auditDocuments` | `id` | `auditId_createdAt`: `[auditId, createdAt]` |
| `auditVoiceDrafts` | `id` | `auditId`, `elementId`, `sessionId` |
| `auditTemplates` | `[id, version]` | `id` |
| `auditRuleSets` | `[id, version]` | `id` |

Существующие `observations`, `photos`, `projects` и их индексы не изменяются. Миграция не читает и не преобразует маршрутные записи, не удаляет фотографии без связанного наблюдения. На пустой базе создаются также прежние хранилища; на базе v1 добавляется отсутствующее `projects`.

Upgrade выполняется одной транзакцией. Несовместимая схема нового хранилища вызывает откат всей миграции, включая номер версии базы. При обнаружении более новой версии возвращается `VERSION_MISMATCH`; понижение версии и удаление базы не выполняются.

## Сохранение и конфликт двух вкладок

Для создания обследования используется `expectedRevision: 0`. Первая сохранённая ревизия равна 1. Каждому принятому пакету команд соответствует ровно одна следующая ревизия и одно событие. Отсутствующая запись при `expectedRevision > 0` возвращает `failed` с кодом `NOT_FOUND`.

`commit` копирует запрос до ожидания открытия базы. Затем открывает общую `readwrite`-транзакцию на `audits` и `auditEvents`, читает актуальную запись и сравнивает её ревизию с ожидаемой. Несовпадение возвращает `conflict` с актуальным агрегатом; функция применения команд и операции записи не выполняются.

После проверки применяется синхронный reducer. Номер ревизии и время изменения назначает слой хранения. Запись агрегата и события коммита атомарна: ошибка в любой записи откатывает обе. ID события равен `transactionId`; повторное использование этого идентификатора возвращает `DUPLICATE_TRANSACTION` с откатом транзакции. Событие содержит автора, команды, время и предыдущую/новую ревизии. Это локальная техническая история, а не удостоверение личности автора.

В текущем шаге атомарный commit изменяет агрегат и событие. Хранилища фото, документов, голосовых черновиков, форм и правил созданы; операции с их содержимым добавляются вместе с соответствующими доменными сценариями. Подготовку изображений, файлов и контрольных сумм необходимо выполнять до открытия транзакции.

## Уведомления и соединения

Локальные подписчики и `BroadcastChannel('urbanaccess_audit_sync')` уведомляются только из `transaction.oncomplete`. Межвкладочное сообщение содержит тип события, `auditId`, `revision`, `transactionId`, `tabId`. Полный текст обследования и фотографии по каналу не передаются. Получатель перечитывает данные через `load`.

Ошибки подписчиков или недоступность канала не отменяют завершённое сохранение. Контроль ревизий работает и без BroadcastChannel. Проверка при фокусе страницы относится к будущему UI. `subscribe` возвращает функцию отписки.

При `blocked` открытие возвращает `UPGRADE_BLOCKED` и вызывает необязательный `onBlocked`. Нужно закрыть блокирующие вкладки и повторить открытие. Поздний запрос, уже завершившийся ошибкой или отменой, не выполняет миграцию.

При `versionchange` соединение закрывается автоматически, кеш соединения сбрасывается, вызывается `onVersionChange`. Неожиданное закрытие также сбрасывает кеш и вызывает `onClose`. `AuditDatabase.close()` отменяет незавершённое открытие и закрывает соединение; затем менеджер можно открыть заново. `AuditStore.close()` закрывает канал и подписки; этот экземпляр больше не используется. Переданный извне менеджер базы закрывает его владелец.

## Подключение к приложению

В шагах 0.5 и 0.6 слой подключён к React-каркасу. Старый `frontend/src/db.js` переэкспортирует общий `openDatabase()` из нового слоя и открывает версию 3. Самостоятельный кеш соединения и upgrade старого модуля удалены. Маршрутные данные доступны через `LegacyRoutesHost`; чтение и экспорт проверяются на production-сборке. Подробности в [описании React и PWA](11-react-saving-and-pwa.md).

## Проверки

После установки зависимостей по `pnpm-lock.yaml`:

```sh
pnpm run typecheck:storage
pnpm test
pnpm run test:storage
```

Для последней команды требуются Playwright и установленный Chromium. Как и существующие браузерные проверки, тест может использовать отдельно установленный Playwright; путь к его модулю можно задать через `PLAYWRIGHT_MODULE_PATH`. Тест сам компилирует три модуля во временную папку, запускает локальный сервер на свободном порту и открывает две страницы одного origin. После проверки браузер, сервер и временная сборка закрываются. Production-база пользователя не затрагивается: проверки выполняются в отдельном браузерном контексте с тестовыми именами баз.

Проверено 15 групп сценариев в Chromium с нативной IndexedDB: новая база, миграции v1/v2, AC-15 с двумя страницами, конкурентное создание, отсутствие BroadcastChannel, откат ошибок, повторный ID транзакции, уведомление после записи, blocked, versionchange, откат upgrade, отмена открытия, некорректные запросы/асинхронные обработчики и закрытие подписок. AC-19 проверен сравнением исходных и полученных записей, схем прежних хранилищ и байтов Blob, включая фотографию без наблюдения. Пользовательская интеграция AC-19 дополнительно проверена в браузерных тестах React-каркаса.
