# Scope

## 1. Цель проекта

Создать демонстрационный прототип информационной системы, которая позволяет собирать, проверять и актуализировать данные о препятствиях в пешеходной среде и использовать подтвержденные данные при построении маршрутов с учетом различных профилей мобильности.

Проект рассчитан на один тестовый район или отдельный пешеходный маршрут.

---

# 2. Входит в проект

## 2.1. Сбор наблюдений

Система позволяет пользователю создать наблюдение о состоянии городской среды и указать:

- местоположение;
- тип препятствия;
- фотографию;
- измеряемые параметры;
- комментарий;
- время наблюдения.

Система автоматически сохраняет автора и время создания записи.

---

## 2.2. Работа с препятствиями

Для подтвержденных наблюдений система должна позволять формировать и хранить данные о препятствии.

Поддерживаются следующие типы:

- бордюр;
- лестница;
- ограждение;
- шлагбаум;
- недостаточная ширина прохода;
- разрушенное покрытие;
- перекрытый тротуар;
- другие препятствия, определенные в справочнике.

Препятствие может иметь точечную, линейную или площадную геометрию.

---

## 2.3. Проверка и модерация

Для пользовательских наблюдений предусматривается процесс проверки:

1. создание наблюдения;
2. автоматическая проверка данных;
3. поиск возможных дубликатов;
4. передача записи на модерацию;
5. подтверждение, отклонение или запрос уточнения;
6. публикация подтвержденного препятствия.

Для каждого решения сохраняется история изменений.

---

## 2.4. Актуальность данных

Система хранит:

- время наблюдения;
- время проверки;
- время последнего подтверждения;
- текущий статус препятствия;
- историю изменения статусов.

Предусматривается возможность обозначить препятствие как требующее повторной проверки.

---

## 2.5. Географические данные

Используются:

- OpenStreetMap как источник базовых данных о пешеходной сети;
- PostgreSQL + PostGIS для хранения и обработки пространственных данных;
- пешеходный граф для маршрутизации.

Система должна уметь связывать подтвержденное препятствие с ближайшим или затрагиваемым участком пешеходной сети.

---

## 2.6. Маршрутизация

Пользователь может выбрать профиль мобильности:

- обычный пешеход;
- человек на инвалидной коляске;
- человек с детской коляской.

Для каждого профиля задаются собственные ограничения и правила оценки проходимости маршрута.

Подтвержденные препятствия должны влиять на построение маршрута в зависимости от выбранного профиля.

---

## 2.7. Отображение на карте

Пользователь должен иметь возможность:

- видеть подтвержденные препятствия;
- открыть карточку препятствия;
- посмотреть фотографии и основные характеристики;
- увидеть дату последнего подтверждения;
- построить маршрут с выбранным профилем мобильности.

---

# 3. Не входит в проект

Следующие функции сознательно исключаются из первой версии:

- отдельное нативное мобильное приложение;
- полноценная социальная сеть пользователей;
- система пользовательских рейтингов и репутации;
- игровые механики;
- автоматическое распознавание препятствий по фотографии;
- машинное обучение;
- автоматическое определение состояния объекта по изображениям;
- интеграция с реальными городскими службами;
- автоматическая отправка обращений в городские службы;
- общегородской или общенациональный охват;
- обработка большого количества внешних источников данных;
- сложная система уведомлений;
- сложная ролевая модель корпоративного уровня;
- промышленное масштабирование и отказоустойчивость;
- учет дорожной ситуации в реальном времени.

Эти возможности могут рассматриваться как дальнейшее развитие проекта.

---

# 4. Минимально жизнеспособная версия (MVP)

Минимально жизнеспособная версия должна поддерживать следующий сценарий:

**Пользователь создает наблюдение → система сохраняет данные → выполняется проверка на возможный дубликат → модератор проверяет запись → подтвержденное препятствие появляется на карте → препятствие связывается с участком пешеходного графа → пользователь строит маршрут с выбранным профилем мобильности → маршрут учитывает подтвержденное препятствие.**

# 6. Пользователи системы

В рамках MVP используются следующие роли:

### Полевой пользователь

Создает наблюдения и добавляет фотофиксацию.

### Модератор

Проверяет наблюдения и управляет их статусами.

### Пользователь маршрута

Выбирает начальную и конечную точки и профиль мобильности.

### Администратор

Используется только для первоначального наполнения и настройки справочников.

Один человек технически может выполнять несколько ролей.

---

# 7. Основные сценарии

В рамках MVP реализуются следующие сценарии:

**UC-01. Создание наблюдения**

Пользователь фиксирует препятствие и передает его в систему.

**UC-02. Добавление фотофиксации**

Пользователь прикладывает одно или несколько подтверждающих изображений.

**UC-03. Проверка возможного дубликата**

Система ищет существующие препятствия в пространственной близости.

**UC-04. Модерация наблюдения**

Модератор подтверждает, отклоняет запись или запрашивает уточнение.

**UC-05. Объединение дубликатов**

Модератор объединяет несколько наблюдений, относящихся к одному препятствию.

**UC-06. Изменение состояния препятствия**

Подтвержденное препятствие переводится в другое состояние после повторной проверки или устранения.

**UC-07. Просмотр препятствий на карте**

Пользователь изучает препятствия на выбранной территории.

**UC-08. Построение маршрута**

Пользователь задает начало, конец и профиль мобильности.

**UC-09. Построение маршрута с учетом препятствий**

Система исключает или повышает стоимость недоступных участков маршрута в зависимости от выбранного профиля.

---

# 8. Граница системы

В состав системы входят:

```text
Система аудита доступности
├── прием наблюдений
├── хранение данных
├── модерация
├── управление состояниями
├── пространственная обработка
└── построение маршрутов
```

Внешними системами и источниками являются:

```text
Пользователь
Модератор
OpenStreetMap
Картографический интерфейс
Хранилище фотографий
```

---

# 9. Внешние интеграции

## OpenStreetMap

Используется как источник базовой информации о пешеходной сети.

## Хранилище фотографий

Используется для хранения файлов, приложенных к наблюдениям.

## Картографический интерфейс

Используется для отображения объектов и маршрутов.

Интеграция с городскими информационными системами в MVP отсутствует.

---

# 10. Ограничения проекта

- Продолжительность разработки: 2–3 недели.
- Территория: один тестовый район или один маршрут.
- Объем демонстрационных полевых данных: ориентировочно 30–50 наблюдений.
- Основной акцент: системный анализ, пространственная модель данных и логика маршрутизации.
- Мобильный клиент не разрабатывается.
- Работа с фотографиями ограничивается необходимым для демонстрации функционалом.
- Маршрутизация проверяется на заранее подготовленных сценариях, а не на всех возможных маршрутах города.

# 12. Критерий завершения MVP

MVP считается завершенным, если пользователь может:

**создать наблюдение → добавить фото → пройти процесс модерации → получить подтвержденное препятствие → увидеть его на карте → построить маршрут с выбранным профилем мобильности, при этом маршрут учитывает подтвержденное препятствие.**

---

# 13. Дальнейшее развитие

После MVP возможны:

- более подробные профили мобильности;
- дополнительные типы городской инфраструктуры;
- автоматический анализ фотографий;
- интеграция с городскими службами;
- мобильное приложение;
- аналитическая панель для городских служб;
- расширение территории покрытия.
