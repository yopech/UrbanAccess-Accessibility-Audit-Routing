# Scope

## 1. Цель проекта

Создать демонстрационный прототип информационной системы, которая позволяет собирать, проверять и актуализировать данные об ограничениях пешеходной проходимости, связывать их с участками пешеходной сети и использовать подтвержденные сведения при построении маршрутов с учетом различных профилей мобильности.

Проект рассчитан на один тестовый район или отдельный пешеходный маршрут.

---

# 2. Входит в проект

## 2.1. Сбор наблюдений

Система позволяет пользователю создать наблюдение о проблеме пешеходной проходимости.

Пользователь указывает:

* положение проблемы на карте;
* тип препятствия;
* характер ограничения;
* фотографию;
* при необходимости — физические характеристики;
* комментарий;
* время наблюдения.

### Определение положения

Система может получить исходную позицию устройства через GPS.

Полученная позиция используется как предварительная точка и может содержать информацию о точности определения местоположения.

Пользователь должен иметь возможность вручную уточнить положение наблюдения, переместив булавку на карте.

В MVP пользователь не обязан самостоятельно создавать точную геометрию физического объекта.

---

## 2.2. Геометрия пользовательского наблюдения

В MVP пользовательское Observation имеет **точечное положение**.

Точка означает:

> место, в котором пользователь зафиксировал ограничение пешеходной проходимости.

Она не обязана совпадать с геометрическим центром физического объекта и не должна рассматриваться как его точная геометрия.

Пользователь не обязан:

* рисовать протяженность забора;
* обходить объект по периметру;
* измерять длину препятствия;
* создавать полигон перекрытой территории.

---

## 2.3. Работа с препятствиями

Для подтвержденных наблюдений система должна позволять формировать и хранить Barrier.

Barrier представляет устойчиво идентифицированное ограничение пешеходной проходимости, объединяющее наблюдения об одном ограничении.

Barrier не обязан иметь отдельную геометрию физического объекта.

Поддерживаются следующие типы:

* бордюр;
* лестница;
* ограждение;
* шлагбаум;
* недостаточная ширина прохода;
* разрушенное покрытие;
* перекрытый тротуар;
* другое препятствие.

---

## 2.4. Связь наблюдений и препятствий

Одно препятствие может иметь несколько наблюдений:

* от разных пользователей;
* сделанных в разное время;
* с разными фотографиями;
* с разными измерениями.

Если новое Observation с высокой уверенностью относится к существующему Barrier, оно может быть автоматически связано с ним.

Если уверенность недостаточна или данные противоречат существующему Barrier, решение принимает модератор.

---

## 2.5. Пространственное влияние

Пространственное влияние Barrier на пешеходную сеть хранится отдельно от пользовательского Observation.

Для каждого подтвержденного Barrier система должна иметь возможность определить один или несколько затрагиваемых участков пешеходной сети.

Например:

```text
Barrier #12
    ├── влияет на Edge 304
    ├── влияет на Edge 305
    └── влияет на Edge 306
```

Для одного пешеходного участка могут существовать несколько источников влияния.

Расширение области влияния протяженного Barrier происходит:

* автоматически на основании новых наблюдений о том же Barrier;
* либо вручную по решению модератора.

Система не обязана заранее определять полную длину или площадь физического объекта.

---

## 2.6. Проверка и модерация

Для пользовательских наблюдений предусматривается процесс:

1. создание наблюдения;
2. автоматическая проверка данных;
3. поиск существующих препятствий-кандидатов;
4. автоматическое сопоставление при высокой уверенности;
5. передача неоднозначных случаев на модерацию;
6. подтверждение, отклонение или запрос уточнения;
7. создание нового Barrier либо присоединение наблюдения к существующему Barrier.

Для решений модератора сохраняется история.

---

## 2.7. Актуальность данных

Система хранит:

* время наблюдения;
* время проверки;
* время последнего наблюдения;
* время последнего подтверждения;
* текущий статус Barrier;
* историю изменения статусов.

Предусматривается возможность обозначить препятствие как требующее повторной проверки.

---

## 2.8. Измерения

Физические измерения являются необязательными.

Пользователь не обязан самостоятельно измерять:

* длину забора;
* площадь перекрытой территории;
* длину участка плохого покрытия.

Параметры, которые могут быть вычислены из пространственных данных системы, рассчитываются автоматически.

Например:

* длина затрагиваемого участка пешеходной сети;
* количество затрагиваемых участков;
* протяженность связанного набора пешеходных участков.

Физические характеристики, например высота бордюра или ширина прохода, могут быть указаны пользователем как дополнительные данные.

---

## 2.9. Географические данные

Используются:

* OpenStreetMap как источник базовых данных о пешеходной сети;
* PostgreSQL + PostGIS для хранения и обработки пространственных данных;
* пешеходный граф для маршрутизации.

---

## 2.10. Маршрутизация

Пользователь может выбрать профиль мобильности:

* обычный пешеход;
* человек на инвалидной коляске;
* человек с детской коляской.

Для каждого профиля задаются собственные ограничения и правила оценки проходимости маршрута.

Подтвержденные препятствия должны влиять на построение маршрута в зависимости от выбранного профиля.

---

## 2.11. Отображение на карте

Пользователь должен иметь возможность:

* видеть подтвержденные препятствия;
* видеть участки пешеходной сети, затронутые ограничениями;
* открыть карточку препятствия;
* посмотреть фотографии и основные характеристики;
* увидеть дату последнего подтверждения;
* построить маршрут с выбранным профилем мобильности.

---

# 3. Не входит в проект

Следующие функции сознательно исключаются из первой версии:

* отдельное нативное мобильное приложение;
* необходимость измерять физические объекты с помощью LiDAR;
* автоматическое создание точной геометрии физического объекта по GPS-треку;
* полноценный графический редактор геометрии уровня профессиональных GIS-систем;
* полноценная социальная сеть пользователей;
* система пользовательских рейтингов и репутации;
* игровые механики;
* автоматическое распознавание препятствий по фотографии;
* машинное обучение;
* автоматическое определение состояния объекта по изображениям;
* интеграция с реальными городскими службами;
* автоматическая отправка обращений в городские службы;
* общегородской или общенациональный охват;
* обработка большого количества внешних источников данных;
* сложная система уведомлений;
* промышленное масштабирование и отказоустойчивость;
* учет дорожной ситуации в реальном времени.

---

# 4. Минимально жизнеспособная версия (MVP)

Минимально жизнеспособная версия должна поддерживать следующий сценарий:

**Пользователь получает предварительную геопозицию → уточняет положение проблемы булавкой на карте → выбирает тип и характер ограничения → добавляет фото → система проверяет данные и ищет существующие препятствия → при высокой уверенности Observation автоматически связывается с Barrier, в неоднозначном случае запись направляется модератору → подтвержденное препятствие связывается с одним или несколькими участками пешеходного графа → пользователь строит маршрут с выбранным профилем мобильности.**

Для протяженных ограничений несколько Observation могут постепенно расширять множество затрагиваемых участков одного Barrier.

# 6. Пользователи системы

### Полевой пользователь

Создает наблюдения и добавляет фотофиксацию.

### Модератор

Проверяет наблюдения и управляет их статусами и связями с Barrier.

### Пользователь маршрута

Выбирает начальную и конечную точки и профиль мобильности.

### Администратор

Используется для первоначального наполнения и настройки справочников.

Один человек технически может выполнять несколько ролей.

---

# 7. Основные сценарии

**UC-01. Создание наблюдения**

Пользователь фиксирует место ограничения и передает его в систему.

**UC-02. Уточнение положения**

Пользователь вручную корректирует предварительную GPS-позицию на карте.

**UC-03. Добавление фотофиксации**

Пользователь прикладывает одно или несколько изображений.

**UC-04. Автоматическое сопоставление с существующим Barrier**

Система определяет, относится ли новое наблюдение с высокой вероятностью к уже существующему препятствию.

**UC-05. Модерация неоднозначного наблюдения**

Модератор принимает решение о создании нового Barrier, присоединении Observation к существующему Barrier или отклонении записи.

**UC-06. Изменение состояния препятствия**

Подтвержденное препятствие переводится в другое состояние после повторной проверки или устранения.

**UC-07. Пространственное сопоставление**

Система определяет участки пешеходного графа, на которые влияет Barrier.

**UC-08. Расширение влияния Barrier**

Новые Observation о том же Barrier могут добавлять новые затрагиваемые участки пешеходной сети.

**UC-09. Ручное уточнение влияния**

Модератор может добавить или удалить затрагиваемые участки пешеходной сети в неоднозначных случаях.

**UC-10. Просмотр препятствий на карте**

Пользователь изучает ограничения на выбранной территории.

**UC-11. Построение маршрута**

Пользователь задает начало, конец и профиль мобильности.

**UC-12. Построение маршрута с учетом препятствий**

Система исключает или повышает стоимость недоступных участков маршрута в зависимости от выбранного профиля.

# 8. Граница системы

В состав системы входят:

```text
Система аудита доступности
├── прием наблюдений
├── уточнение положения
├── хранение данных
├── сопоставление наблюдений с препятствиями
├── модерация
├── управление состояниями
├── определение пространственного влияния
├── сопоставление с пешеходным графом
└── построение маршрутов
```

Внешними системами и источниками являются:

```text
Пользователь
Модератор
OpenStreetMap
Картографический интерфейс
Хранилище фотографий
```

# 9. Внешние интеграции

## OpenStreetMap

Используется как источник базовой информации о пешеходной сети.

## Хранилище фотографий

Используется для хранения файлов, приложенных к наблюдениям.

## Картографический интерфейс

Используется для уточнения положения, отображения препятствий, затронутых участков и маршрутов.

Способ предоставления мобильного интерфейса является отдельным техническим решением. В MVP может использоваться мобильный веб-интерфейс или интерфейс внутри Telegram.

Интеграция с городскими информационными системами отсутствует.

---

# 10. Ограничения проекта

* Продолжительность разработки: 2–3 недели.
* Территория: один тестовый район или один маршрут.
* Объем демонстрационных полевых данных: ориентировочно 30–50 наблюдений.
* Основной акцент: системный анализ, пространственная модель данных и логика маршрутизации.
* Точное картографирование физической геометрии препятствий не является задачей пользователя.
* Геометрия пользовательского Observation ограничивается точкой.
* Сложная автоматическая обработка GPS-треков не входит в MVP.
* Полная протяженность физического Barrier не определяется автоматически на основании одного Observation.
* Маршрутизация проверяется на заранее подготовленных сценариях, а не на всех возможных маршрутах города.

# 12. Критерий завершения MVP

MVP считается завершенным, если пользователь может:

**получить предварительную геопозицию → уточнить положение проблемы на карте → зафиксировать наблюдение → добавить фото → пройти автоматическое или ручное сопоставление с Barrier → получить подтвержденное препятствие → увидеть его на карте → связать его с одним или несколькими участками пешеходного графа → построить маршрут с выбранным профилем мобильности, при этом маршрут учитывает влияние препятствия.**

Дополнительно для протяженного ограничения должно быть возможно продемонстрировать, как несколько наблюдений расширяют множество затрагиваемых участков одного Barrier.
